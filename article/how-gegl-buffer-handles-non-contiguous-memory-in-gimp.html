How GeglBuffer Handles Non-Contiguous Memory in GIMP

This article provides an overview of how the Generic Graphics Library (GEGL) powers GIMP's memory infrastructure through the GeglBuffer tile management system. Rather than forcing the operating system to allocate single, massive blocks of linear memory for high-resolution images, GeglBuffer partitions pixel data into independent, uniform tiles managed via an indexed hierarchy. This approach allows GIMP to efficiently handle non-contiguous memory allocations, dynamic paging, and smooth canvas manipulation without relying on contiguous address space.

The Tile-Based Architecture

Traditional image processing relies on large, flat raster buffers where pixels are laid out sequentially in memory. For massive or multi-layered canvases, this demands enormous contiguous blocks of RAM that frequently lead to memory fragmentation and allocation failures. GeglBuffer circumvents this by subdividing the 2D image plane into uniform, rectangular units called tiles (typically 128×128 or 64×64 pixels).

Each tile represents an isolated payload of raw pixel data that is allocated individually on the heap. Because each tile is an independent entity, the total memory required for an image can be scattered across physically non-contiguous locations in system memory.

Indexing and Sparse Allocation

To manage non-contiguous tiles without performance degradation, GeglBuffer uses a spatial coordinate system mapped through internal index structures. When an operation addresses a coordinate (x, y) on the canvas, the system divides the coordinates by the tile dimensions to determine the tile index.

This index maps to an array or hash-based lookup structure managed by GeglTileSource and GeglTileBackend. This decoupled architecture enables sparse storage:

  • Unallocated Regions: Empty or transparent canvas areas do not require allocated memory until drawn upon.
  • Lazy Allocation: Tiles are only brought into physical memory when explicitly read or written to.
  • Shared Storage: Redundant or duplicate tiles (such as fully transparent blocks across multiple layers) can point to a single shared, copy-on-write memory reference.

Linearization for Filters and Operations

While non-contiguous storage is optimal for system memory, graphics processing operations often require linear memory arrays to perform convolution, color correction, and blending efficiently. GeglBuffer bridges this gap using memory access abstractions rather than exposing raw tile pointers directly to operations.

Developers interact with non-contiguous data through APIs such as gegl_buffer_get() and gegl_buffer_set(), as well as GeglBufferIterator. When a process requests a region of interest (ROI) that spans across multiple non-contiguous tiles, the iterator fetches the relevant tiles, linearizes their contents into a small, temporary contiguous buffer, and feeds it to the processing pipeline. Once the operation finishes, the iterator distributes the modified data back into their respective non-contiguous tile destinations.

Caching and Disk Swapping via GeglTileCache

Because tiles exist as distinct memory entities, GeglBuffer incorporates a sophisticated caching subsystem called GeglTileCache. The cache tracks tile activity using a Least Recently Used (LRU) algorithm.

When GIMP approaches configured RAM thresholds, GeglTileCache does not need to defragment or relocate the entire image. Instead, it serializes inactive, non-contiguous tiles individually to disk-backed swap files. When those tiles are required again, they are loaded back into any available, arbitrary memory addresses, completely freeing GIMP from the constraints of host memory contiguity.
