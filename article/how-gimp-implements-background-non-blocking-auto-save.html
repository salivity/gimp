How GIMP Implements Background Non-Blocking Auto-Save

This article explores how the GNU Image Manipulation Program (GIMP) writes large background auto-save files without freezing the user interface. It examines the architectural combination of GEGL tile management, state snapshotting, asynchronous worker threads via GLib, and atomic file system operations that collectively enable non-blocking disk I/O.

The Challenge of Background Saving

Large image files often contain multiple high-resolution layers, masks, and undo history, totaling gigabytes of uncompressed memory. Writing this volume of data directly from the main application thread causes the graphical user interface (GUI) to hang, as the GTK main event loop cannot process user input while waiting for synchronous disk I/O. To prevent interface locking, GIMP decouples the serialization process from the primary thread.

GEGL Buffer Architecture and Snapshotting

At the core of GIMP’s modern image handling is GEGL (Generic Graphics Library). GEGL does not treat an image as a single contiguous array in RAM. Instead, it organizes image data into a sparse grid of fixed-size blocks called tiles (typically 128x128 or 64x64 pixels).

When an auto-save process begins, GIMP must ensure that subsequent user edits do not mutate the data being written to disk. GIMP and GEGL resolve this through reference counting and copy-on-write (CoW) semantics:

  1. Buffer Duplication: GIMP creates a shadow reference or duplicate of the GeglBuffer. Because GEGL relies on reference-counted tile indices, duplicating a buffer is near-instantaneous and does not duplicate the actual pixel memory immediately.
  2. Copy-on-Write: If the user draws on the canvas while the background save is running, the main thread allocates new tiles for the modified regions. The background task retains read-only access to the original tiles as they existed at the exact moment the auto-save was triggered.

Offloading I/O via GLib Worker Threads

Once the image state is isolated, GIMP offloads the serialization and file-writing tasks using GLib's threading infrastructure (GThread, GThreadPool, or GTask):

  • Thread Dispatch: The main thread spawns or assigns the serialization job to a background worker thread.
  • Data Serialization: The worker thread iterates over the frozen GEGL tiles, processes compression algorithms (such as RLE or zlib compression used in the XCF format), and formats the output data.
  • Asynchronous Streams (GIO): GIMP utilizes GIO file streams (GOutputStream) to write the serialized chunks to disk. This ensures that the operating system handles the block-level I/O operations asynchronously relative to the main UI thread.

Atomic Disk Writing

To prevent file corruption if the program crashes or the system shuts down during an auto-save, GIMP performs atomic writes:

  1. Data is written to a temporary file (e.g., filename.xcf.tmp) in the background.
  2. The background thread flushes the file descriptor to ensure all data is physically committed to disk.
  3. Once the write operation succeeds, the worker thread informs the main thread via an idle callback (g_idle_add()).
  4. The file is renamed to its final target path using an atomic file system operation (rename()), instantly replacing the previous save file without intermediate corruption.
